# Evertrail AI system

## Architecture

React profile form → Supabase Edge Function `trek-intelligence` → bounded public catalog query → deterministic filtering/scoring → top candidate context → OpenAI-compatible model → Zod validation → React results.

The provider key is read only inside the Edge Function. The browser invokes the function through `supabase.functions.invoke`. Supabase Auth authenticates private saves; RLS scopes preferences, saved plans, packing progress, feedback and wishlists to the current user.

## Implemented source paths

- `src/components/ai/planner.tsx`: profile and trip steps, matches, comparisons, feedback, saves.
- `supabase/functions/_shared/trek-engine.ts`: validated preferences, weighted scoring, exclusions, preparation factors.
- `supabase/functions/trek-intelligence/index.ts`: match, plan, compare and chat actions; catalog retrieval; Open-Meteo forecast retrieval; provider request/validation.
- `src/components/ai/plan-view.tsx`: generated day guidance, known route facts, weather, checklist and export.
- `src/components/ai/trek-chat.tsx`: global chat. Questions are independently retrieved; earlier messages are not supplied as conversational context. Users explicitly save conversation snapshots.
- `src/app/dashboard/ai-plans/page.tsx`: owned history, rename, export, delete, modify preferences and itinerary regeneration.

## Deterministic scoring

Fitness 20%, experience 20%, budget 15%, season 15%, duration 10%, difficulty 10%, terrain/interest compatibility 10%. Component values are deterministic integers, combined and rounded. These are heuristic compatibility scores, NOT probabilities of safe completion and not clinically validated ratings.

The database query excludes prices above budget, durations above available days and altitudes above the user ceiling. Application filtering additionally checks location, season, declared altitude concerns, challenging-route experience/fitness and optional real-departure availability. Sample records are never treated as live inventory. Equal scores use slug ordering for reproducibility.

Only the top three suitable matches are sent for explanations. Alternatives show rule-based exclusions or lower component scores. Items removed by the initial SQL constraints are described collectively, not individually. The catalog query is capped at 100 records; larger catalogs need paginated or SQL-side ranking before this can claim exhaustive recommendations.

## Facts and generation

Names, prices, durations, distances, altitude and departures are rendered from database records. Scores are not generated by the model. Explanation references must match supplied IDs. Zod constrains output structure; prose rejects numeric digits/currency symbols, while authoritative numeric facts render separately.

This validation is NOT a guarantee that all natural-language claims are factually correct. A model can still produce unsupported qualitative statements or spell numbers as words. Operator review and stronger claim-level validation remain necessary before production safety use.

Seed records are explicitly illustrative. Their daily route stages are absent. The UI therefore shows unknown routes, times and elevation changes rather than fabricating operational itineraries. Generated days are preparation/activity guidance until operator stages exist.

## Weather and risk

Open-Meteo uses catalog coordinates for a selected date within its forecast window. Out-of-range dates and API failures return explicit unavailable states. Sample coordinates are approximate and forecasts are not summit forecasts. Numeric forecast values are never estimated locally.

Preparation levels are simple rule-based heuristics derived primarily from altitude, difficulty and concerns. Weather challenge remains unspecified in the current risk score; weather is displayed separately with the generated plan. Technical route difficulty is marked undocumented. This is not a medical diagnosis or emergency service.

## Failure behavior

Missing `OPENAI_API_KEY` is reported on an actual request. Matching and comparison may return rule-based scores with `aiError` and no fabricated explanations. Plans and chat return an error rather than a fake generation. Gateway/network errors are shown in the UI.

The endpoint currently uses a shared database-backed hourly cap of 120 requests and 20 per verified user. Anonymous users share the global cap; this is a cost guard, not comprehensive abuse protection. Production needs per-client protection and separate quotas for free matching vs paid model calls.

## Storage and remaining scope

Current tables: `treks`, `trek_departures`, `profiles`, `user_preferences`, `ai_plans`, `packing_lists`, `ai_feedback`, `wishlists`, `ai_request_limits`.

Recommendations, comparisons, conversations and itineraries currently use typed JSON snapshots in `ai_plans`; packing progress uses a string array. The originally requested normalized recommendation/day/message/item tables have not been implemented. No weekly-match dashboard, recently-viewed personalization, automated history persistence, operational booking integration, or fully contextual multi-turn chat is implemented. Explorer/detail pages still use the separate local sample catalog; production must unify these with Supabase to prevent divergence.

## Verification status

The live AI tests check the deployed endpoint first. A 404 is a deployment blocker, not a passing fallback test. Live model generation requires credentials and must be tested separately from missing-key behavior. Browser TypeScript checks exclude the Deno runtime directory; successful Next.js compilation does not establish Deno runtime correctness.
